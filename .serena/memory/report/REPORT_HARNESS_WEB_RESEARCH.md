## Implications for Our Harness

**Tool doctrine (Serena/LSP vs grep):**

- LSP token cost is model- and codebase-dependent, not a flat win: Sonnet pays +118% premium for symbol lookups where Opus pays only +6%. Our main-agent model choice should factor into any blanket "Serena-first" rule.
- Serena's clearest win is precision on noisy-naming codebases and cross-file reference/rename safety, not raw token cost on clean/small codebases — scope "Serena before Read/Edit" doctrine to cross-file reference/rename tasks; reconsider forcing it for single-file/clean-naming lookups where grep is cheaper and equally correct.
- Multi-file rename via LSP location-only is _worse_ than grep (Pass@1 0.67 vs 1.00) unless inline context is added — prefer the dedicated `rename_symbol` tool (handles this correctly) over manual `find_referencing_symbols` + edit when doing renames across files; if going manual, always pull surrounding context, not just file:line.

**Gates (docs-first, sweep, doc-gate, agent-model):**

- The GATED_CALL_BUDGET=15 "one docread unlocks 15 gated calls" model is directionally consistent with prompt-cache economics (pay once, amortize reads) but no external benchmark validates 15 specifically — flag as untested, not validated, if reviewed later.
- Subagent exemption from the docs-first gate is well-supported: issue #97076 shows subagent spawn cost is dominated by inherited context/schemas, not doc-lookup cost — stacking a docs gate on top of that would compound an already-expensive failure mode.

**Subagent delegation:**

- Issue #97076's measured ~11x spawn-cost gap (60,236 vs 5,332 tokens) directly supports tool-restricted subagent profiles (e.g., our Explore-type agents) over default full-context spawns — worth confirming our `agents/*` definitions actually restrict tools/MCP connectors rather than inheriting everything by default.
- The same issue's routing bug (orchestrator instructions overridden by the user's raw last chat line; 24/25 agents refused work) is concrete external evidence for keeping our `[swe-steering-contract]` pattern (spawned agents trust the orchestrator's prompt, not stray content) — worth verifying it holds through multi-hop delegation (sub-agent spawning its own sub-agent).
- 3.2M tokens burned across two 26-agent workflows (mostly spawn overhead, not work) argues for capping fan-out width and reusing/resuming named agents via SendMessage rather than spawning fresh agents per subtask.

**Memory loading:**

- Issue #29971's numbers (500KB/session from CLAUDE.md re-injection; ~1.25M tokens/session from skill/MCP duplication at scale; 607K-token system prompt in one mode) validate this project's hub+children memory split (e.g., DOM_SWE_HOOKS hub with topic children) as the correct mitigation shape for the exact failure class measured.
- No external source validates or invalidates this project's specific size thresholds (ok≤8,000/warn≤16,000/split/unreadable≥50,000 chars) — these remain internally derived, not externally benchmarked.
- The "silent truncation past ~200 lines" claim is anecdotal, not an Anthropic-confirmed hard limit — do not adopt as a firm cutoff, but it supports the general direction of keeping root memories/CLAUDE.md short.

**Baseline size:**

- Anthropic's own 2025-09-29 guidance (keep CLAUDE.md lean, push domain detail to referenced files, let subagents return distilled summaries) remains the best primary-source backing available for this project's hub/child memory split and thin-CLAUDE.md posture — no later 2026 primary source supersedes it.
- The 214,300-token built-in-subagent overflow (#84947) is a cautionary upper bound: whatever is added to custom agent system prompts/tool schemas has a hard ceiling before the agent becomes undispatchable; worth periodically checking total schema+prompt size for this project's custom agents.
